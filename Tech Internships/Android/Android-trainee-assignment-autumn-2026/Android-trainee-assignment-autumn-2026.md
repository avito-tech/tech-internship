## **Тестовое задание для стажёра Android (осенняя волна 2026\)**

Необходимо разработать Android-приложение для работы с заметками и задачами.

Приложение состоит из трёх основных разделов:

* Заметки;  
* Задачи;  
* Настройки.

Основная навигация между разделами осуществляется с помощью Bottom Navigation Bar

---

# **Экран списка заметок**

## **Состав экрана**

Экран должен содержать:

* Floating Action Button для создания новой заметки;  
* список сохранённых заметок;  
* строку поиска (см. раздел «Поиск и сортировка»);  
* кнопку сортировки (см. раздел «Поиск и сортировка»);  
* кнопку переключения режима удаления.

По нажатию на Floating Action Button пользователь переходит на экран создания заметки.

Каждый элемент списка должен содержать:

* изображение-превью заметки или заглушку, если изображение отсутствует;  
* название заметки;  
* дату создания заметки.

По нажатию на заметку пользователь переходит на экран просмотра и редактирования заметки.

Заметки должны сохраняться между запусками приложения (см. раздел «Как хранить данные»).

## **Удаление заметок**

При включении режима удаления на всех элементах списка должна появляться кнопка удаления.

По нажатию на неё соответствующая заметка удаляется.

Пока включён режим удаления, остальные действия с элементами списка должны быть недоступны.

---

# **Экран создания и редактирования заметки**

Один и тот же экран используется для:

* создания новой заметки;  
* просмотра существующей заметки;  
* редактирования существующей заметки.

При открытии существующей заметки на экране должны отображаться сохранённые ранее данные.

## **Состав экрана**

Экран должен содержать:

* поле для ввода заголовка;  
* поле для ввода текста заметки;  
* возможность добавить изображение;  
* предпросмотр выбранного изображения;  
* возможность удалить выбранное изображение;  
* кнопку «Сохранить»;  
* кнопку голосового ввода (см. раздел «Голосовой ввод»).

## **Требования**

* Каждая заметка должна содержать непустой заголовок.  
* Текст заметки может быть пустым.  
* Пользователь может добавить изображение из файлов устройства или сделать фотографию с помощью камеры.  
* Если к заметке добавлено изображение, оно должно отображаться как превью в списке заметок.  
* Если изображения нет, в списке должна отображаться заглушка.  
* Пользователь должен иметь возможность удалить ранее выбранное изображение.  
* Перед использованием камеры, файлов устройства или микрофона необходимо корректно запросить необходимые разрешения.  
* Необходимо обрабатывать ситуацию, когда пользователь не предоставил требуемое разрешение.  
* После сохранения заметки изменения должны отображаться в списке заметок.  
* Данные заметки должны сохраняться между запусками приложения (см. раздел «Как хранить данные»).

# **Экран задач**

Экран предназначен для просмотра, создания и управления задачами.

## **Состав экрана**

Экран должен содержать:

* App Bar;  
* строку поиска (см. раздел «Поиск и сортировка»);  
* фильтр по статусу;  
* список задач;  
* Floating Action Button для создания новой задачи.

Каждая задача должна содержать:

* название;  
* checkbox;  
* статус выполнения.

Задача может находиться в одном из двух состояний:

* активная;  
* выполненная.

Задачи должны сохраняться между запусками приложения (см. раздел «Как хранить данные»).

## **Создание задачи**

По нажатию на Floating Action Button пользователь выбирает способ создания задачи:

* текстовый ввод;  
* голосовой ввод (см. раздел «Голосовой ввод»).

### **Текстовый ввод**

При выборе текстового ввода непосредственно в списке создаётся новый элемент задачи с активным полем ввода.

Отдельный экран или Bottom Sheet для создания задачи использовать не нужно.

После завершения ввода необходимо:

* проверить, что название задачи не пустое;  
* сохранить задачу;  
* перевести элемент списка в обычное состояние.

## **Статус задачи**

При изменении состояния Checkbox статус задачи должен обновляться и сохраняться.

Выполненная задача должна:

* визуально отличаться от активной — например, с помощью уменьшенной прозрачности или зачёркнутого текста;  
* отображаться ниже активных задач.

Сортировка задач выполняется в соответствии с общими требованиями (см. раздел «Поиск и сортировка»).

## **Состояния экрана**

Необходимо предусмотреть как минимум следующие состояния:

* отображение списка задач;  
* пустой список;  
* создание задачи с помощью текстового ввода;  
* запись голоса;  
* обработка голосового запроса;  
* ошибка.

Во время длительных операций пользователю должен отображаться индикатор загрузки.

Ошибки должны корректно обрабатываться и отображаться пользователю.

После добавления или изменения задачи список должен обновляться автоматически.

# **Экран настроек**

Экран позволяет пользователю настроить внешний вид приложения и посмотреть доступный баланс токенов GigaChat.

## **Состав экрана**

Экран должен содержать:

* информацию об оставшемся количестве токенов GigaChat;  
* настройку темы приложения:  
  * системная;  
  * светлая;  
  * тёмная;  
* настройку цветовой схемы;  
* кнопку «Сбросить настройки».

Выбранные настройки должны сохраняться между запусками приложения (см. раздел «Как хранить данные»).

## **Баланс GigaChat**

Для получения актуального остатка токенов необходимо использовать метод [get-balance](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/get-balance).

Необходимо предусмотреть:

* состояние загрузки;  
* успешное отображение баланса;  
* состояние ошибки.

## **Настройка темы**

Пользователь должен иметь возможность выбрать:

* системную тему;  
* светлую тему;  
* тёмную тему.

Изменение темы должно применяться без перезапуска приложения.

## **Цветовая схема**

Пользователь должен иметь возможность выбрать основной цвет приложения из заранее заданного набора.

Выбранный цвет должен применяться к акцентным элементам интерфейса, например:

* кнопкам;  
* переключателям;  
* активным элементам навигации;  
* другим акцентным компонентам.

Цветовая схема должна:

* корректно работать со светлой и тёмной темой;  
* применяться сразу после выбора;  
* сохраняться между запусками приложения.

Необходимо предусмотреть цветовую схему по умолчанию.

## **Сброс настроек**

По нажатию на кнопку «Сбросить настройки» тема и цветовая схема должны возвращаться к значениям по умолчанию.

# **Голосовой ввод**

Голосовой ввод используется:

* при вводе текста заметки;  
* при создании задачи.

Для распознавания речи можно использовать [SaluteSpeech API](https://developers.sber.ru/docs/ru/salutespeech/overview).

## **Общий сценарий**

При запуске голосового ввода необходимо:

1. Запросить разрешение на использование микрофона, если оно ещё не предоставлено.  
2. Начать запись речи пользователя.  
3. После завершения записи отправить аудиозапись на распознавание.  
4. Получить распознанный текст.  
5. Использовать полученный текст в соответствии с текущим сценарием.

Во время работы необходимо отображать соответствующие состояния интерфейса:

* запись речи;  
* обработка;  
* ошибка.

Ошибки записи, распознавания или обработки должны корректно отображаться пользователю.

## **Голосовой ввод заметки**

После распознавания речи полученный текст добавляется в поле текста заметки.

## **Голосовое создание задачи**

После распознавания речи необходимо:

1. Получить текст из аудиозаписи.  
2. Отправить текст в GigaChat для обработки.  
3. Получить итоговый текст задачи.  
4. Создать и сохранить задачу.  
5. Добавить её в список.

Во время обработки на экране задач должен отображаться индикатор загрузки.

---

# **Поиск и сортировка**

Поиск и сортировка используются на экранах списка заметок и задач.

## **Поиск**

Поиск выполняется по названию элемента.

При выполнении поиска на экране должны отображаться только элементы, названия которых соответствуют поисковому запросу.

Если строка поиска пуста, должен отображаться полный список.

Поиск должен запускаться по нажатию на кнопку поиска или кнопку Search на клавиатуре.

Способ реализации поиска остаётся на ваше усмотрение. Можно использовать:

* возможности выбранной базы данных;  
* стороннюю библиотеку;  
* собственную реализацию.

## **Сортировка**

При нажатии на кнопку сортировки должно открываться меню со следующими вариантами:

* от новых элементов к старым;  
* от старых элементов к новым.

Сортировка должна применяться к текущему отображаемому списку — как к полному списку, так и к результатам поиска.

Для задач выполненные задачи при этом должны оставаться ниже активных.

---

# **Как хранить данные**

Данные приложения должны храниться локально и восстанавливаться после перезапуска приложения.

К таким данным относятся:

* заметки;  
* задачи;  
* выбранная тема;  
* выбранная цветовая схема;  
* другие пользовательские настройки.

Для хранения заметок и задач можно использовать:

* **Room**;  
* SQLDelight;  
* SQLite API из Android SDK.

Способ хранения пользовательских настроек остаётся на ваше усмотрение.

После создания, изменения или удаления данных соответствующие экраны должны автоматически отображать актуальное состояние.

---

# **Навигация**

Для реализации навигации необходимо использовать Navigation Compose.

Основная навигация приложения должна быть реализована с помощью Bottom Navigation Bar с тремя вкладками:

* Заметки;  
* Задачи;  
* Настройки.

С экрана списка заметок должна быть предусмотрена навигация:

* на экран создания новой заметки;  
* на экран просмотра и редактирования существующей заметки.

# **На что мы будем обращать внимание**

При оценке тестового задания для нас важен не только объём реализованной функциональности.

В первую очередь мы будем смотреть на:

* корректность работы реализованных сценариев;  
* качество и читаемость кода;  
* структуру и архитектуру приложения;  
* работу с состоянием UI;  
* работу с асинхронными операциями;  
* обработку ошибок и пограничных случаев;  
* работу с локальным хранилищем;  
* качество интеграции с внешними API;  
* понимание Android SDK и Jetpack Compose;  
* обоснованность принятых технических решений.

Если какие-либо требования не удалось реализовать полностью, это **не является причиной не отправлять решение**.

Мы понимаем, что объём задания достаточно большой и за ограниченное время реализовать абсолютно все пункты может быть сложно. Проекты с частично реализованным функционалом также принимаются и будут рассмотрены.

В такой ситуации рекомендуем:

* сосредоточиться на качестве уже реализованной функциональности;  
* обеспечить стабильную работу основных сценариев;  
* описать в README, какие части задания реализованы, какие не реализованы и что вы бы сделали дальше при наличии дополнительного времени.

Дополнительная функциональность не обязательна для успешного выполнения тестового задания. Лучше качественно реализовать основные сценарии, чем пытаться добавить все дополнительные возможности в ущерб качеству решения.
