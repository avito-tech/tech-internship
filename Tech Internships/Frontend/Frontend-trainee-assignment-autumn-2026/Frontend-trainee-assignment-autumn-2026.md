## **Тестовое задание для стажёра Frontend (осенняя волна 2026\)**

### **Система бронирования переговорных комнат**

Разработайте веб\-приложение, в котором сотрудник может найти свободную переговорную, забронировать её и управлять своими бронированиями.

Backend API, real-time API, документация, тестовые данные и макеты интерфейса предоставляются вместе с заданием. Авторизацию и backend реализовывать не нужно.

**Технические требования:**

* Node.js 20+  
* React 18+  
* TypeScript  
* `react-router-dom`  
* предоставленный backend API  
* WebSocket или Server-Sent Events для real-time обновлений  
* публичный Git-репозиторий  
* `README.md` с инструкцией по запуску и описанием выбранных технологий

Можно использовать любые UI-библиотеки, сборщик, менеджер состояния и библиотеки для работы с API, формами и датами.

**Функциональные требования:**

* офис обязателен для отображения переговорных  
* бронирование создаётся только на будущее время  
* рабочие часы всех офисов — с 09:00 до 20:00 по локальному времени  
* минимальная продолжительность — 15 минут  
* начало и продолжительность выбираются с шагом 15 минут  
* бронирование доступно не более чем на 30 дней вперёд  
* бронирования одной комнаты не могут пересекаться  
* отменить можно только собственное будущее бронирование  
* backend является источником истины и повторно проверяет ограничения

**Маршруты:**

* `/rooms` — список переговорных  
* `/rooms/:roomId` — переговорная и её расписание  
* `/bookings` — бронирования пользователя

Маршрут `/` должен перенаправлять на `/rooms`. Для неизвестного маршрута необходимо показать страницу «Ничего не найдено».

**Макеты интерфейса:** [Figma](https://www.figma.com/design/VuCFeHjoXSSYSz5jpANMTg/%D0%91%D1%80%D0%BE%D0%BD%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5-%D0%BF%D0%B5%D1%80%D0%B5%D0%B3%D0%BE%D0%B2%D0%BE%D1%80%D0%BD%D1%8B%D1%85?node-id=0-1&t=nJL8YR7n5UwMRCLg-1), а также архив с макетами приложен отдельным файлом на случай отсутствия доступа к Figma. Интерфейс должен в целом соответствовать макетам — присутствовать нужные экраны, формы, состояния и навигация. Пиксельное совпадение не требуется, функциональность важнее визуальной точности.

**Обязательная часть:**

* список комнат и основные фильтры  
* расписание одной комнаты  
* создание и отмена бронирования  
* обработка 409 (конфликт бронирования)  
* базовое real-time обновление открытого расписания  
* loading/error/empty состояния  
* покрытие кода юнит-тестами

**Дополнительные задания** (приступаем только после реализации основных):

* reconnect с resync и отображением состояния соединения  
* real-time обновление всего списка комнат  
* оптимистическая отмена с rollback  
* экспорт .ics  
* повторяющиеся бронирования

**Real-time обновления:** Для обновлений используем WebSocket. Клиент должен обрабатывать события создания и отмены бронирований, а также изменения доступности переговорной.

Без перезагрузки страницы должны обновляться:

* доступность комнат на выбранный интервал  
* расписание открытой переговорной

*(Обработка потери соединения — переподключение, повторная загрузка данных, индикатор состояния — часть дополнительного задания «reconnect с resync», см. выше.)*

**Результат.** Репозиторий должен содержать:

1. Исходный код приложения  
2. `README.md` с инструкцией по запуску  
3. Описание архитектуры и выбранных технологий  
4. Инструкцию по запуску тестов

Не требуется реализовывать авторизацию, административную панель, управление офисами и переговорными, приглашение участников или интеграцию с корпоративным календарём.

Использование AI-инструментов при разработке разрешено, однако на следующих этапах отбора вас могут попросить объяснить любой фрагмент написанного кода.

Если у вас возникнут вопросы, ответы на которые не описаны в требованиях, принимайте решения самостоятельно. В таком случае, добавьте в README-файл раздел с описанием принятых решений и обоснованием выбора.
